# wifi-ui

Веб-интерфейс для первоначальной настройки Wi-Fi на встраиваемом
устройстве (Raspberry Pi и подобные): устройство поднимает точку доступа,
телефон подключается к ней, открывает страницу и выбирает домашнюю сеть
из списка, как на роутерах или умных колонках.

Часть проекта [robogarage](.) - робот на Raspberry Pi с распознаванием
QR-кодов и жестов.

## Идея

**UI полностью отделён от бэкенда.** `index.html` не знает, что у него
за спиной - свой скрипт на `nmcli`, comitup, либо что угодно ещё. Он общается
только через 4 JSON-эндпоинта (контракт ниже), поэтому бэкенд можно
менять, не трогая фронт вообще.

## Структура репозитория

**Фронт**
- `index.html` - вся страница целиком (HTML+CSS+JS в одном файле, без
  внешних зависимостей: шрифтов из CDN, npm-пакетов и т.п.). Это важно, ведь
  устройство в режиме хотспота обычно без интернета, так что подключить
  Google Fonts или React с CDN не выйдет.

**Бэкенды** (в проде используется один, остальные для разработки/теста)
- `server.py` - бэкенд для Pi: реальные вызовы `nmcli`.
- `mock_server.py` - заглушка с фейковыми сетями для теста UI на
  компьютере без Pi и без реального Wi-Fi.
- `overlay_server.py` - альтернативный бэкенд поверх установленного из
  apt comitup (переиспользует его D-Bus-клиент и state machine, отдаёт
  `index.html` вместо родных шаблонов comitup).
- `comitup_harness.py` - тестовый стенд для сравнения нашего UI и
  оригинального UI comitup бок о бок на компьютере, без Pi и без D-Bus.

**Настройка и деплой на Pi** (для варианта с `server.py`)
- `setup_hotspot.sh` - разово создаёт профиль точки доступа в NetworkManager.
- `start-network.sh` - при загрузке пробует известные сети, иначе поднимает хотспот.
- `robogarage-network.service`, `robogarage-web.service` - systemd-юниты для автозапуска.
- `DEPLOY.md` - пошаговая инструкция по заливке на Pi.

## Быстрый старт (без Pi)

```bash
pip install flask
python3 mock_server.py
# открыть http://localhost:8080
```

Если открыть `index.html` вообще без бэкенда (просто двойным кликом),
страница сама переключится в демо-режим с фейковыми сетями - это удобно,
чтобы быстро посмотреть дизайн.

## Контракт API

### `GET /api/status`

```json
{
  "state": "hotspot",
  "device_name": "robogarage-042",
  "ssid": null,
  "ip": null,
  "message": ""
}
```

`state`: `hotspot` | `scanning` | `connecting` | `connected` | `failed`.
`ssid` - сеть, к которой подключены/подключаемся. `ip` - адрес после
успешного подключения. `message` - текст ошибки при `state == "failed"`.

### `GET /api/networks`

```json
[
  { "ssid": "MyHomeWifi", "signal": 78, "secured": true }
]
```

`signal` - число 0–100, список лучше сортировать по убыванию.

### `POST /api/connect`

Тело: `{ "ssid": "...", "password": "..." }`

Отвечает сразу `{"ok": true}` и не блокирует запрос, сама попытка
подключения идёт в фоне. Фронт после этого раз в 1.5 сек опрашивает
`/api/status`, пока `state` не станет `connected` или `failed`.

### `POST /api/rescan` (необязательно)

Если не реализован, то фронт просто заново дёргает `/api/networks`.

## Тест с настоящим comitup на компьютере (без Pi)

`mock_server.py` - это условная заглушка, без comitup вообще. Если нужно
проверить именно с реальным кодом comitup (его state machine, шаблоны
и т.д.) — используй `comitup_harness.py`.

Настоящий `comitup_web` тянет `comitup.client`, а тот на верхнем уровне
модуля делает `import dbus` и лезет в системный D-Bus без установленного
`dbus-python`, живого демона comitup и NetworkManager это упадёт сразу
при импорте. Так что напрямую погонять comitup_web на компьютере нельзя.

`comitup_harness.py` обходит это тем же способом, что и собственные тесты
comitup (`test/test_web.py`) - подменяет `comitup.client` фейковым
объектом до импорта, с той же формой ответов, но без D-Bus и без реального
Wi-Fi. Сам Flask-app, роуты и шаблоны настоящие, из `comitup_web/comitupweb.py`.

```bash
git clone https://github.com/davesteele/comitup.git
cp comitup_harness.py index.html comitup/
cd comitup
pip install flask cachetools
python3 comitup_harness.py
```

Дальше доступны сразу два адреса на одних и тех же фейковых данных,
чтобы было удобно сравнивать бок о бок:

- `http://localhost:8080/` - оригинальный UI comitup, как есть
- `http://localhost:8080/ui/` - наш `index.html`, но через адаптер
  `/api/*`, добавленный поверх того же fake-client

## Почему свой nmcli-бэкенд, а не готовое решение

Рассматривались comitup, balena-wifi-connect, python-wifi-connect и RaspAP.

| | язык | API из коробки | автопортал/mDNS |
|---|---|---|---|
| comitup | Python/Flask + D-Bus | почти нет (HTML-рендер) | есть из коробки |
| balena wifi-connect | Rust | JSON API есть | есть из коробки |
| python-wifi-connect | чистый Python, stdlib | JSON, минимальный | нет |
| RaspAP | PHP + FastAPI | REST API + плагины | есть, но проект - полноценный роутер-панель, избыточен для задачи |
| свой nmcli (`server.py`) | Python/Flask | наш собственный `/api/*` | нет (пока) |

comitup и balena надёжнее по части автоматики (перехват портала, mDNS),
но comitup - это постоянно работающий демон, который может конфликтовать с
подключениями в обход его собственного клиента, а balena - скомпилированный
Rust-бинарник, который нельзя ни прочитать, ни доработать напрямую. Свой
nmcli-бэкенд менее зрелый, зато весь код читаемый и полностью
контролируется — включая будущее расширение под вторую задачу (передачу
параметров сервера управления роботом), для которой ни в одном из готовых
решений нет штатного механизма.

## Дизайн

Тёмная техническая панель (не связано ни с одной библиотекой стилей):
моноширинный шрифт для SSID/статусов/IP, системный sans для заголовков,
сигнал сети - не эмодзи, а bar-график по 4 полоскам, тонкая сканирующая
полоса в шапке во время поиска сетей. Всё на системных шрифтах, никакого
интернета для отрисовки страницы не требуется.
